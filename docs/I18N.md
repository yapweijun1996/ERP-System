# Internationalization (i18n)

This document is the implementation contract for the browser UI. The application
supports five left-to-right interface languages:

| App code | Interface language | `Intl` / HTML language |
| --- | --- | --- |
| `en` | English | `en-SG` |
| `ms` | Bahasa Melayu | `ms-MY` |
| `zh` | Simplified Chinese | `zh-Hans` |
| `ja` | Japanese | `ja-JP` |
| `vi` | Vietnamese | `vi-VN` |

## 1. Boundary: UI language is not company localization

i18n controls browser UI copy and presentation. Company localization controls tax,
currency, statutory reports, document numbering and document/report locale. They are
orthogonal:

| | UI i18n | Company localization |
| --- | --- | --- |
| Scope | Current browser | `company_fn` |
| Controls | Labels, actions, validation, status display, notifications, UI formatting | Tax, currency, statutory rules, exported/printed document locale |
| Example | A Mandarin UI | A Singapore GST company using SGD |

The UI translates every system-authored visible string, including navigation, fields,
buttons, dialogs, empty states, validation, notifications, accessibility names and
known API outcomes. It translates the display label for stable enums, but never changes
their API/database/export code.

The following remain in their source language and must not be passed through `t()`:

- user-entered or imported business records;
- company, partner, employee, product and custom-role names;
- document numbers, identifiers and audit facts;
- CSV/PDF/invoice/PO/statutory output, which keeps its own explicit locale/company rule.

## 2. Resolution, persistence and fallback

The current Web client resolves language as follows:

```text
active language = localStorage("aria-lang") when it is one of en/ms/zh/ja/vi
               -> en
```

It does not infer language from the browser, URL or active company. The preference is
browser-local and is not synced to the user account. The existing `app_user.language`
field is retained for schema compatibility but the current Web client does not read or
write it.

Translation lookup is deterministic:

```text
active pack -> English -> explicit fallback -> key
```

A missing non-English key still falls back to English at runtime as an intentional
safety contract, but it is a blocking finding in the current static release audit.
A completed release therefore ships with no known missing keys or unreviewed
system-authored fallback text.

## 3. Resource and loading contract

- English is the canonical key set and is available synchronously with the application.
- `ms`, `zh`, `ja` and `vi` are independent, module-namespaced locale packs loaded only
  when requested.
- Only plain strings and plural-form objects are allowed. Locale resources must not
  contain HTML or Markdown.
- A target pack is parsed and structurally validated before activation. Switching is
  atomic: failure keeps the current language and stored preference and shows a retryable
  notice.
- Concurrent requests for the same pack share one promise.
- English is always available offline. A successfully used non-English pack enters the
  Service Worker runtime cache and can then be used offline.
- If a saved non-English pack is unavailable during offline startup, the session renders
  English without overwriting the saved preference and retries when connectivity returns.

Keys use stable module namespaces such as `inventory.product.name`. English keys are
never repurposed with a new meaning; introduce a new key when semantics change.

## 4. Runtime API and message rules

The compatibility globals remain available:

```text
getLang()                         -> en | ms | zh | ja | vi
getLocale()                       -> BCP-47 locale from the table above
t(key, params?)                   -> translated string
tf(key, fallback, params?)        -> translated string with explicit fallback
ts(value, params?)                -> translated stable enum/status display label
setLang(code)                     -> Promise<boolean>
applyI18n(root?)                  -> update bound UI nodes in place
formatDate(value, options?)
formatDateTime(value, options?)
formatNumber(value, options?)
formatCurrency(value, currency, options?)
```

Named interpolation uses `{name}`. When `params.count` is present and a translation is
a plural object, `Intl.PluralRules` selects the language form. All interpolated values
are treated as text and escaped at the DOM boundary. Rich presentation is composed by
UI components rather than embedded in translations.

The HTTP error envelope keeps stable `error.code`, English `error.message` and
`requestId`. It may add structured `params` and field-error codes. The browser translates
known codes and uses the English message for unknown codes; the server does not localize
responses.

## 5. Formatting and live switching

- Display dates and numbers follow the active UI locale in the table above.
- Currency uses the record/company currency and original numeric value; language never
  converts currency.
- Date-only values remain the same calendar date and must not shift through UTC parsing.
- Timestamps remain UTC at rest and display in the browser time zone.
- Machine inputs retain canonical ISO dates and raw decimal values.

Changing language must not reload or navigate. `applyI18n()` updates bound text,
placeholder, tooltip, title, ARIA and formatted-value nodes in place, then emits
`erp:localechange` for charts and custom controls. Form values, dirty state, filters,
pagination, scroll, focus and open dialogs remain unchanged.

## 6. Quality and release gates

The repository i18n audit enforces:

- valid locale resource structure and supported value types;
- identical placeholder names across translated variants;
- no HTML/Markdown in resources;
- no newly hardcoded system-authored UI copy after the zero baseline;
- explicit allowlisting for business samples and user-controlled content.

Missing non-English keys and hardcoded system-authored copy are blocking findings in the
current static gate; their English fallback remains a runtime safety path and is tested.
Every i18n release must run all Canonical routes in all five languages, plus representative
desktop and phone interactions. Current static inventory passes at **1,545 English keys /
72 local packs**. TASK-183 records a **129 routes × 5 languages × 2 viewports** browser
checkpoint; TASK-194 did not rerun it because local Playwright Chromium is absent.
Acceptance requires zero runtime errors, raw keys, known hardcoded system copy or
page-level horizontal overflow; static success alone is not a current browser pass.

Company Receipt Pack `locale` is currently stored but the PDF renderer hard-codes English,
uses standard Helvetica and replaces non-ASCII characters. TASK-202 must use localized
resources and an embedded Unicode font; an untranslated/corrupted exported artifact is an
i18n correctness defect, not an acceptable business-data exception.

None of the supported languages is right-to-left, so RTL layout is outside this release.
