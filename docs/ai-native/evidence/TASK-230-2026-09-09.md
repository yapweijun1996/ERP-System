## S1 — Choose a supported protocol/auth topology

### Decision record

| Decision | Selected contract | Boundary and reason |
| --- | --- | --- |
| MCP transport | Streamable HTTP, JSON response mode where the SDK transport supports it | The official TypeScript SDK recommends Streamable HTTP for remote servers; legacy HTTP+SSE is compatibility-only. The server will use the SDK lifecycle rather than a hand-written JSON-RPC subset. |
| Protocol version | MCP `2025-11-25` | `@modelcontextprotocol/sdk@1.30.0` reports `2025-11-25` as its latest and supported protocol version. It is pinned exactly in `package.json` and `package-lock.json`. |
| Versioned resource | `/api/mcp/v1` | The canonical resource URI is the absolute deployment origin plus this path, for example `https://erp.example.test/api/mcp/v1`. Clients must bind the OAuth `resource` indicator and token audience to this URI. |
| Protected-resource discovery | RFC 9728 metadata at the path/root well-known location plus a `WWW-Authenticate` `resource_metadata` challenge on 401 | The future endpoint will advertise the configured authorization-server issuer and required scopes. No issuer URL is invented or hardcoded as a production authority. |
| Authorization service | External OAuth 2.1/OIDC authorization server configured by deployment | ERP is the protected resource server. Its adapter must validate issuer signature/introspection, audience/resource, expiry, revocation and scopes, then map the validated subject to the ERP Agent principal/grant. Platform cookies, browser sessions and impersonation are not accepted. |
| Least-privilege scopes | `erp.receipts.read`, `erp.receipts.prepare`, `erp.receipts.execute` | `read` covers bounded receipt/Pack reads and export; `prepare` covers non-authorizing reviewed facts; `execute` is still insufficient by itself because TASK-233 exact intent and human approval/confirmation remain authoritative. ERP action grants and field allowlists are checked per call. |
| Client registration | Deployment-selected pre-registration, CIMD or DCR according to the authorization server | The ERP server does not hand-roll an OAuth authorization server in this repository. S4 will use two distinct clients: official TypeScript SDK `@modelcontextprotocol/sdk@1.30.0` and official Python SDK `mcp==1.27.2` on its maintained v1 line for the `2025-11-25` protocol. |

The local adapter is intentionally a fixture, not a production issuer. It stores
only a SHA-256 digest of bounded opaque test tokens in memory, checks the configured
issuer/resource audience, expiry, revocation and required scopes, and returns the
same `AuthenticatedAgentIdentity` contract consumed by the existing Agent boundary.
It does not accept tenant, Company, actor or grant claims from a request body. The
future production adapter must perform cryptographic JWT/JWKS or introspection
validation before the same ERP principal/grant resolution; the ERP command remains
the source of truth for tenant scope, permissions and G06 approval.

## S2 — Implement endpoint and discovery

### Transport and boundary implementation

S2 adds `src/api/routes/mcp.ts` and mounts it before the human-session module gate in
`src/api/app.ts`. The endpoint is the versioned `POST/GET/DELETE` resource
`/api/mcp/v1`; the server uses the official `StreamableHTTPServerTransport` in
stateless JSON-response mode and the SDK `McpServer` lifecycle for every request.
The stateless choice is deliberate: authentication is evaluated on every HTTP
request, so an initialized MCP session cannot pin a stale tenant or grant identity.

Only the six version-1 G01 actions are registered, using the existing action
catalogue descriptions and the existing `dispatchAuthenticatedAgentAction`
boundary:

- `receipt.search`
- `receipt.get`
- `receipt_pack.prepare`
- `receipt_pack.create`
- `receipt_pack.get`
- `receipt_pack.export`

The adapter exposes the G01 `{ action, version, body }` envelope as MCP
`structuredContent`. PDF export retains the governed metadata and returns the
bounded PDF as an embedded MCP resource; no arbitrary SQL, route or database
operation is registered.

### Discovery, authentication and limits

- RFC 9728 protected-resource metadata is served at
  `/.well-known/oauth-protected-resource/api/mcp/v1` and the root well-known
  alias, advertising only the configured issuer and the three configured ERP
  receipt scopes.
- An unauthenticated endpoint request returns `401` with a
  `WWW-Authenticate` `resource_metadata` challenge. There is no browser-cookie
  or anonymous fallback.
- The configured adapter receives the fixed resource URI, request method/path,
  request id and action-derived required scopes. `receipt_pack.prepare` requires
  read + prepare; `receipt_pack.create` requires read + execute; all other pilot
  calls require read. ERP principal, Company, module, grant, field and approval
  checks remain in the shared dispatcher.
- Express bounds inbound JSON at 1 MB. MCP input schemas are strict and action
specific. The initial S2 implementation bounded tool results at 1 MB, with binary
resources counted by their base64 representation; S4 measured the existing
multilingual Pack PDF and raised the current bounded default to 50 MB with a
100 MB hard cap. Each tool call has a 10 second execution timeout. Domain and
contract failures become structured MCP tool errors.

### S2 exit evidence

The new `src/api/mcp.integration.test.ts` uses the official TypeScript SDK client
`Client` plus `StreamableHTTPClientTransport` against a real local HTTP server and
fresh PGlite database. It observed:

1. unauthenticated POST → HTTP 401 and an RFC 9728 `resource_metadata` challenge;
2. protected-resource discovery → HTTP 200 with the configured resource, issuer and
   least-privilege scopes;
3. client initialization → protocol `2025-11-25`;
4. `tools/list` → exactly the six G01 pilot tools and their contract description;
5. `tools/call receipt.search` → structured `{ action: "receipt.search", version: 1,
   body: { data: [], meta: { scope: "company", limit: 10 } } }` from the governed
   Agent grant/tenant dispatcher.

This is local PGlite and local issuer-fixture evidence. It does not claim a
production OAuth/OIDC issuer, deployed endpoint, rate-limit proof, two-client
interoperability, cross-Company negative matrix or safe timeout replay; those are
S3-S5 responsibilities.

## S3 — Enforce authorization on every call

### Fail-closed authorization decisions

S3 closes the gap between an issuer adapter contract and the MCP route boundary.
`src/api/routes/mcp.ts` now revalidates the returned identity's exact configured
issuer and resource audience, verifies that the returned scopes contain every
scope required by the request, and computes scope requirements across all messages
in a JSON-RPC batch. The adapter is called for every HTTP request, including
initialization, tools/list and tools/call; no browser cookie, human session or
client-supplied Company is used.

The existing `dispatchAuthenticatedAgentAction` remains the only business entry
point after MCP authentication. Therefore a guessed Company enters the issuer-
derived transaction only to fail the existing Agent principal/grant/module checks;
it cannot widen visibility or create a Pack. `receipt_pack.create` continues to
require the TASK-233 exact intent and current approval state. A pre-commit human
cancel changes the intent to `cancelled`, and the MCP tool returns a structured
`agent_execution_intent_not_approved` error before any Pack row is written.

### S3 exit evidence

`src/api/mcpAuthorizationBoundary.integration.test.ts` uses a fresh PGlite
database, real local HTTP servers and the local token-digest fixture. It passes

  token and a token missing the `prepare` scope; each is rejected with HTTP 401;

## S4 — Prove two-client interoperability

### Client and fixture identity

S4 uses two distinct official MCP client implementations against the same fresh
PGlite-backed local HTTP server and the same issuer-derived Agent identity:

  `Client` + `StreamableHTTPClientTransport`.
- Python official SDK `mcp==1.27.2`, installed in the disposable external
  environment `/tmp/erp-system-mcp-s4-venv` from
  `tests/e2e/mcp-python-client-requirements.txt`. The environment is not part of
  the repository and the script never prints the bearer token.

The fixture uses only `M1` / `C-SG`, a dedicated Agent principal and six
company-scoped grants for the six G01 actions. It creates one clean receipt with
known document/version identity and a fixed reviewed date range. No production
database, OAuth issuer, customer credential or deployed host is involved.

### Real protocol flow and persisted postconditions

`src/api/mcpInteroperability.integration.test.ts` drives the official TypeScript
client through protocol `2025-11-25` to initialize, list exactly six tools, search,
read one receipt, exercise bounded pagination/empty-page and invalid-input errors,
prepare the exact selection and inspect the SHA-256 digest. It then creates a
human-approved exact G06 intent and sends `receipt_pack.create` through a fetch
wrapper that consumes and drops the response after the server commit. The test
queries the database rather than trusting that failed client call: exactly one
Pack exists and its row contains the expected receipt identity/version.

The official Python client then initializes against the same endpoint, lists the
same six tools, searches the same receipt, replays the exact create payload and
receives the original Pack ID with `replayed: true`, attempts the same key with
changed filters and receives `company_receipt_pack_key_conflict`, reads the Pack,
and exports the PDF as an MCP resource. The script decodes the resource bytes and
computes the artifact SHA-256; the test asserts that the decoded byte length and
hash equal the structured export metadata while the source digest remains a
separate value. The database still contains one Pack, one approved intent and
three Pack audit rows (create, replay and export).

The generated local PDF is **28,263,157 bytes** for the existing multilingual
font-backed Pack renderer. Its MCP JSON resource representation is therefore
larger than the previous 1 MB limit. The route now uses a bounded 50 MB default
result budget and 100 MB hard cap so legitimate governed exports are not rejected;
the limit still prevents unbounded MCP responses. Rate-limit capacity and
production sizing remain S5/release evidence.
