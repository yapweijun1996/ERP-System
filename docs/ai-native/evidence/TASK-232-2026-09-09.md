## S2 grants and validation

### Implemented boundary

S2 adds the additive `agent_principal` and `agent_grant` tables in
[agent.ts](../../../src/data/schema/agent.ts), exported from the canonical schema
barrel. Both tables carry `master_fn` and `company_fn`; the production RLS coverage
list includes both tables. `app_user.identity_kind` now accepts `agent` and
`service_automation`, while a new non-human-login check keeps both bridge identities
non-login. Existing human session filters and the hidden `platform_actor` bridge are
unchanged.

`createAgentPrincipal` and `createAgentGrant` in
[agentIdentity.ts](../../../src/modules/agent/agentIdentity.ts) require the current
human caller to hold `admin.users.manage`. Principal creation persists a distinct
non-login `app_user` bridge with a random PBKDF2 hash; no plaintext credential is
returned or stored. The principal stores kind, accountable human owner, lifecycle
status and version without receiving a role assignment or Platform permission.

Grant creation validates all of the following before writing and auditing the row:

- registered action contract and an assignable tenant permission listed by that action;
- pilot action-to-resource mapping and a bounded field allowlist from the current
  Receipt/Receipt Pack projection catalog;
- `self`, `team`, `department` or `company` scope with matching target type and
  accountable-owner binding for `self`;
- effective-dated window, grant version, revocation shape and optional numeric amount
  limit/currency pair;
- current active owner membership and `authorizeWithin` permission/resource/scope
  authority. The owner is an authority intersection input, not an inherited Agent role.

`resolveAgentGrantWithin` re-reads the principal, bridge actor and accountable human
owner on every call. It fails closed for unknown or inactive actors/actions, paused or
revoked principals, inactive owners, expired/revoked grants, scope expansion, fields
outside the allowlist, amount overrun or currency mismatch. It then calls the central
authorization evaluator for the current owner, so a later role/override downgrade is
observed instead of being hidden by a stale delegation row. Decimal comparison is used
for the amount boundary.

## S3 authenticated authorization and audit

### Implemented boundary

`src/auth/agentAuthentication.ts` defines the issuer adapter contract. The issuer
receives only the bearer credential, request method/path and server request id; it
does not receive the action body and returns a verified Agent principal id plus
issuer-derived `masterFn`/`companyFn`, issuer, audience and subject. The ERP layer
does not implement an anonymous fallback or turn a human session cookie into an
Agent credential.

`POST /api/agent/actions` is mounted before the human-session module gate and is
CSRF-exempt only because it requires the separately authenticated Agent bearer
boundary. `src/api/routes/agent.ts` rejects recursive body identity keys (`masterFn`,
`companyFn`, `agentPrincipalId`, actor/owner/session/permission fields) before the
issuer or business dispatcher is called. The body can select only a registered
action and its bounded input. `dispatchAuthenticatedAgentAction` then opens the
issuer-derived tenant transaction, checks the `expenses_tax` entitlement, resolves
the current `agent_principal`/grant and accountable owner's current ERP authority,
and never constructs a human `SessionData` for the Agent.

Existing receipt commands still receive their required numeric business subject as
the accountable owner. The audit subject is separate: `actorUserId` is the
non-login Agent/service bridge, `agentPrincipalId` identifies the true Agent and
`delegatorUserId` identifies the accountable owner. Agent JSON results are projected
through the grant field allowlist; Pack PDF export fails closed unless every Pack
field is granted. Pack export appends its audit event inside the same tenant
transaction as the authorization and artifact read boundary.

Migration `0105_boring_sentinels.sql` adds the Agent/owner audit foreign keys and
indexes. Migration `0106_military_preak.sql` adds the append-only attribution
consistency check: a row with an Agent principal must also carry a true actor and
delegator. Human and Platform audit fields remain compatible. `listEntityAudit`
now exposes the Agent and delegator ids without changing existing actor/platform
semantics.

## S4 lifecycle controls

S4 adds the hash-only `agent_credential` aggregate and migration
`drizzle/0107_small_gambit.sql`. Rotation generates a bearer token once, stores
only its SHA-256 hash and a non-secret hint, revokes the prior active credential
atomically and advances the principal version. Review responses expose status,
window, hint and versions but never `tokenHash` or the raw token.

`src/api/routes/adminAgents.ts` provides human-session and CSRF-protected review,
principal creation, grant creation/revocation, pause/resume/disable/revoke and
one-time credential rotation. The Agent API continues to use the independent
bearer issuer boundary. Disabled/revoked principals revoke their active
credentials (and revoked principals also revoke grants); pause/resume preserves
the grant but the next action rechecks principal status.

## Findings and decisions

- **Resolved migration defect — high for checkpoint integrity:** first disposable migration replay failed because PostgreSQL/PGlite could not use the later-created unique index as the referenced composite FK target. Reproduction was the first `agentIdentity.test.ts` run. Repaired with a table-level unique constraint and regenerated artifacts; the full focused suite then passed.
- **Capability boundary — not a defect:** current ERP role permissions are resource-level, so S2 uses a source-owned pilot field catalog plus grant allowlists and rejects unknown fields. A future shared field-policy system must replace/extend this catalog without weakening the current fail-closed behavior.
- **Resolved S4/S5 security boundary:** the Agent credential table stores only a SHA-256 token hash and hint; the raw rotated token is returned once. Issuer lookup is the only transaction-local `app.agent_issuer` exception, and business reads/writes remain tenant-scoped and grant-authorized.
