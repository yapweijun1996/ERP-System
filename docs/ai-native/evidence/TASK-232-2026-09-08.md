### Current gap reproduced from source

The current `app_user` check constraint accepts only `human` and `platform_actor`; the
session resolver filters to `human`; `AuthorizationPrincipal` has no principal kind or
owner; and `audit_log` has no Agent/owner columns. The current TASK-228 dispatcher also
accepts a real human `SessionData` and intentionally blocks Agent Pack creation with
`agent_action_confirmation_required`. Therefore the existing system can attribute a
human or a Platform operation, but it cannot safely attribute a delegated Agent or
service automation without a new identity boundary.

The existing regression baseline reproduced the preserved behavior: the focused command
passed 4 files / 24 tests in 35.56s. These tests cover active human sessions, session
expiry/revocation/company switching, central authorization, expired/revoked overrides
and authorization-version invalidation. No current test or schema row was treated as
evidence that Agent identity already exists.

## Migration and backward-compatibility decision

Use an additive, separate Agent identity model while retaining a compatibility bridge for
existing numeric actor FKs:

1. Add a tenant-scoped `agent_principal` aggregate with a stable public key, principal
   kind (`delegated_agent` or `service_automation`), accountable human owner, non-login
   actor bridge, lifecycle status/version and timestamps. The principal owns no implicit
   role or Platform permission. A later grant table owns action/resource/field scope,
   time window, amount ceiling, revocation and authorization-version checks.
2. Expand `app_user.identity_kind` with non-login Agent/service values only for the
   bridge rows. Create one bridge row per Agent/service principal, with no password
   login or human session. Existing human rows, sessions, role assignments and
   permission semantics are unchanged; no existing row is backfilled into an Agent.
3. Keep existing commands accepting `actorUserId: number` for compatibility. The Agent
   resolver returns a server-owned context containing the bridge `actorUserId`, true
   `agentPrincipalId`, accountable `ownerUserId`, and session-derived tenant. It may
   project the bridge ID into `AuthorizationPrincipal`, but only after the grant is
   intersected with current tenant/module/resource/field authority. It never constructs
   `SessionData` from JSON and never accepts actor, owner, master or Company authority
   from the request body.
4. Add nullable `agentPrincipalId` and `delegatorUserId` audit references through an
   additive migration and extend `AuditEvent`. Existing human rows retain only
   `actorUserId`; existing Platform rows retain `platformPrincipalId`; new Agent actions
   record the bridge actor, true Agent and accountable delegator in one transaction.
   `api_idempotency.actorUserId` can continue to use the distinct bridge ID, while
   Agent identity/request binding remains explicit in the Agent boundary.
5. Generate the shared Drizzle/schema artifacts and update production RLS coverage in
   the implementation checkpoint. Tenant-scoped Agent/grant rows use the normal
   `master_fn`/`company_fn` policy. If the Agent credential/control table is intentionally
   control-plane exempt, record that exemption and restrict it separately; do not add a
   broad worker flag or a generic RLS bypass.

This design keeps the old business/audit contracts stable without making a service actor
pretend to be its owner. It also keeps issuer authentication separate from ERP business
authorization: a valid Agent credential identifies the principal, while the grant and
current ERP authorization decide what it may do.

## Findings and decisions

- Current code has one human tenant principal shape and one hidden Platform bridge; it has no safe Agent/service principal. The absence is a boundary gap, not a reason to weaken `SessionData` or reuse `platform_actor`.
- Numeric `actorUserId` is a compatibility boundary used by receipt ownership, Pack creator visibility, idempotency and audit FKs. A dedicated Agent principal must bridge to its own non-login `app_user` row while preserving true Agent/owner attribution separately.
- No acceptance-blocking defect was reproduced in the preserved human authorization/session baseline. The task remains open until grants, resolver integration, lifecycle controls and PostgreSQL/RLS proof exist.
