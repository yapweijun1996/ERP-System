## S1 — Verify prerequisites and browser support

### Official API decision

The current official references were checked before probing or implementing the
page adapter:

- [W3C WebMCP draft, 4 September 2026](https://webmachinelearning.github.io/webmcp/): the API is a draft Community Group Report, uses `document.modelContext`, structured tool definitions and page-local execution.
- [Chrome WebMCP imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api): `registerTool`, `getTools`, `executeTool`, lifecycle cancellation through `AbortSignal`, and the `toolchange` event are the current documented surface; the API remains under active discussion and origin-trial/preview support.

The implementation must feature-detect `document.modelContext` first and may
only use `navigator.modelContext` as a compatibility probe for older preview
builds. It must never install a polyfill and must not claim a native tool when
the browser API is absent. Registration remains a thin adapter over the shared
G01 dispatcher/adapter; the browser surface is convenience, not authorization.

## S2 — Register and retire tools

### Implementation

The page adapter is loaded after the legacy shell in
`web/public/assets/erp-webmcp-adapter.js` and is inert unless the browser
provides the documented `document.modelContext.registerTool` function. It
registers exactly the six G01 pilot action names on the active
`company-receipts` route when the authenticated actor has the enabled
`expenses_tax` Company module and one of the governed Company Receipt read
permissions. Each registration uses an `AbortSignal`; `invalidate()` aborts
the previous registration and increments a generation token.

The tool callbacks do not capture actor, Company or permission grants. They
re-read the current `DB.user`, session-derived `DB.erpSystem.scope`, module
projection and route before and after the existing `ErpSystemData` call. A
registration fingerprint rejects a changed actor, Company or capability set;
stale, logged-out, off-route and unauthorized invocations fail closed before
dispatch. `receipt_pack.create` remains confirmation-gated through a separate
visible bridge; the adapter cannot call the normal Pack write method silently.

The shell now invalidates or resynchronizes tools on navigation, logout,
Company switch and module/capability refresh. The API and Demo adapters expose
session-scoped receipt detail, read-only Pack preparation and Pack lookup. The
new `/api/company-receipts/packs/prepare` path reuses the shared Pack selection
query and SHA-256 contract and was verified to return a selection without
inserting a `company_receipt_pack` row.

## S3 — Integrate visible preparation and confirmation

### Implementation

`web/public/assets/screens-company-receipts.js` now treats Pack creation as a
two-step visible workflow. Preview, PDF and Print first call the read-only
`companyReceiptPackPrepare` adapter, which uses the shared tenant-scoped
selection query and returns the selection digest, selected evidence rows,
currency-separated exact totals, filters, counts and preparation metadata. The
screen opens a review modal showing those facts and the pending action; no Pack
write is attempted while that modal is open.

The human must explicitly choose `Confirm and create` before the normal,
session-authorized `companyReceiptPack` command runs. Cancellation closes only
the review and leaves the filter form, route state, focus restoration and page
scroll unchanged. Confirmation re-prepares the same filters and compares the
selection digest before writing; a changed eligible set replaces the review
facts and requires another explicit confirmation. The existing immutable Pack
command remains the write boundary, and PDF view/download/print operate only on
the Pack returned after confirmation. The WebMCP `receipt_pack.create` bridge
uses this same visible review, confirmation and cancellation path; it does not
silently call the normal Pack writer.
