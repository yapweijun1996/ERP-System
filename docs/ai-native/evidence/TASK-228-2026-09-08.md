## S2 strict contracts

The single maintained contract catalogue is [actionContracts.ts](../../../src/modules/agent/actionContracts.ts),
with executable coverage in [actionContracts.test.ts](../../../src/modules/agent/actionContracts.test.ts).
It publishes the six pilot action names at contract version `1` and keeps the
transport boundary separate from session, tenant, database and approval code.

| Action | Availability / effect | Strict input boundary | Pagination / replay | Important contract boundary |
| --- | --- | --- | --- | --- |
| `receipt.search` | Current route / read | Optional `limit` 1–100, positive `afterId`, search ≤200 chars, valid date-only filters | Keyset `afterId` → `nextCursor`; no idempotency | Session-derived active Company; read-only transaction |
| `receipt.get` | Current route / read | Positive `receiptId`, no unknown fields | None | Authorized receipt projection only |
| `receipt_pack.prepare` | Contract only / non-authorizing preparation | Optional search ≤200 chars, required valid ordered date range, supported locale | None; no idempotency | No Pack row, audit or approval grant; approval remains TASK-233 |
| `receipt_pack.create` | Current route / confirmed write | Safe `packKey` 8–128 chars, required valid ordered date range, supported locale | Business-key replay; changed facts return `company_receipt_pack_key_conflict` | Immutable snapshot and audit are the write boundary; Agent confirmation is required before execution |
| `receipt_pack.get` | Current route / read | Positive `packId`, no unknown fields | None | Creator, tenant and downgraded-visibility checks remain fail-closed |
| `receipt_pack.export` | Current route / export | Positive `packId` and `view|download|print` | None | PDF transport declares separate artifact/source digests and preserves export audit |

Runtime input validation rejects unknown fields, invalid calendar dates, invalid
limits and reversed date ranges. It recursively rejects client-supplied authority
fields such as `masterFn`, `companyFn`, `actorUserId`, `scope` and `visibility`,
including when nested in an otherwise unknown object. Runtime output validation
accepts the existing JSON Receipt/Pack envelopes and a normalized PDF metadata
envelope while preserving decimal amounts, currency-separated totals, IDs,
versions and date-only values as strings. The contract lists the current route
authentication, stale-authorization, permission, source, quarantine and storage
failure codes; it does not claim a dispatcher or public Agent transport.

## S3 authenticated shared dispatch and preparation

The shared entry point is [agentActions.ts](../../../src/api/agentActions.ts),
covered by [agentActions.test.ts](../../../src/api/agentActions.test.ts). It accepts
a real typed `SessionData` supplied by an authenticated adapter plus an untrusted
action/input payload. It derives `{ masterFn, companyFn }` from that session,
resolves `read_company` before `read_own`, runs the operation inside
`withTenantTransaction`, and translates existing domain/quarantine/storage errors
to structured `ActionDispatchError` values. No JSON payload is converted into a
session or allowed to replace tenant, actor or permission authority.

The genuinely shared Pack selection query is
`selectCompanyReceiptPackWithin` in [companyReceiptPack.ts](../../../src/modules/expenses/companyReceiptPack.ts).
The existing Pack creation command now calls this same function, while
`receipt_pack.prepare` calls it read-only after the session permission decision.
The shared function preserves ready status, inclusive date bounds, own/company
visibility, bounded 5,000-row selection, deterministic ordering, version/document
identity, decimal arithmetic, currency-separated totals and the source digest.
Preparation returns those authorized versioned rows plus a selection digest and
creates no `company_receipt_pack` row or Pack-created audit. `receipt.search`,
`receipt.get`, `receipt_pack.get` and PDF export also use the shared session and
transaction boundary; export retains its existing append-only `pdf_<action>` audit.

`receipt_pack.create` is deliberately parsed and permission-checked but returns
`agent_action_confirmation_required` (428) until TASK-233 supplies an identity-
bound reviewed approval. The existing human POST path remains available and still
owns its current Pack replay/conflict and audit behavior; no Agent mutation is
publicly exposed by this checkpoint.

S3 result: Pass. The new test covers authenticated search and preparation,
nested tenant-field rejection, no-Pack persistence, approval-gated creation,
current Pack read/export, PDF digest headers and export audit. The S3 focused
suite passed 6 files / 29 tests in 44.45s; backend/Web typechecks, lint, PGlite
Demo and Demo production build exited 0. No real MCP/WebMCP transport claim is
made.

## S5 boundary publication and final verification

The published boundary is the versioned catalogue in
[actionContracts.ts](../../../src/modules/agent/actionContracts.ts) plus the
authenticated dispatcher in [agentActions.ts](../../../src/api/agentActions.ts).
The dispatcher accepts a real `SessionData` from an authenticated adapter and an
untrusted action/input payload; it never accepts tenant or actor authority from that
payload. The shared Pack selection remains owned by
[companyReceiptPack.ts](../../../src/modules/expenses/companyReceiptPack.ts), and
the human route remains the source of truth for Pack creation.

### Supported and unsupported operations

| Boundary | Allowed behavior | Explicit limitation / structured failure |
| --- | --- | --- |
| `receipt.search` | Session-scoped read with bounded keyset pagination, date/search filters and read-company/read-own visibility | Unknown fields or authority injection fail with contract validation; tenant scope is never client-selected |
| `receipt.get` | Session-scoped authorized receipt detail with document/version identity | Foreign or unavailable rows fail closed; invalid IDs and permission failures are structured |
| `receipt_pack.prepare` | Read-only governed selection using the same ready/date/visibility/5,000-row rules as Pack creation; returns versions, totals and selection digest | It creates no Pack, audit or approval grant; approval/intent binding is TASK-233 |
| `receipt_pack.create` | Existing human endpoint remains the confirmed Pack command with immutable snapshot and business-key replay/conflict semantics | Agent dispatch is parsed and permission-checked but returns `agent_action_confirmation_required` (428) until TASK-233; no public Agent mutation is exposed |
| `receipt_pack.get` | Session-scoped immutable Pack read with creator/snapshot visibility checks | Tenant, creator and permission failures remain fail-closed |
| `receipt_pack.export` | Authorized PDF view/download/print with separate artifact/source digests and append-only export audit | It is not effect-free: the existing export audit is retained; source/quarantine/storage failures remain structured |

The boundary does not expose raw SQL, arbitrary receipt-ID selection, purge,
legal-hold, void, payment, tax posting, provider calls, durable Agent runs or a
replacement approval engine. Recoverable failures include contract validation,
permission denial, unavailable/foreign resource, Pack key conflict, source or
quarantine failure, storage failure and the explicit confirmation gate. Retry of the
human Pack command is proven by same-key replay; changed selection intent is rejected
without a second Pack. Cancellation and delegated-grant revocation are not invented
for this stateless foundation and remain downstream TASK-232/TASK-236 responsibilities.
