# TASK-193 — Local tenant account recovery — 2026-09-09

## Scope and result

Company Owner and Master Admin reuse the tenant human-account recovery command.
The login screen now links to a five-language recovery page at
`<public mount>/reset-password`. The page requests email instructions, confirms a
new password and returns the user to sign-in. It does not authenticate the user
from the reset link. The local mail sink captures messages in memory only.

TASK-193 remains **Blocked**. No SMTP configuration, external email, production
migration, deployment or live recovery was performed. Platform Superadmin has a
separate `platform_principal` credential/session boundary and no email recovery
implementation in the current release scope. The tenant endpoint must not reset it.
The task's three-realm acceptance is therefore still incomplete.

## Source-backed gaps and changes

- `src/auth/lifecycle.ts`: confirmation already locked tokens and enforced expiry,
  single use and the Employee-account exclusion, but did not recheck active human
  login eligibility. It now rejects inactive, login-disabled or non-human users
  without consuming the token or changing the password. Existing session revocation
  remains in the same transaction.
- `src/api/routes/auth.ts`: normalize email before constructing the throttle key,
  preventing leading whitespace from splitting one account across keys. Count the
  attempt before token/outbox issuance so issuance failures also count. Public
  responses remain identical for unknown, ineligible and throttled accounts.
- `src/worker/outbox.ts`: raw mail exceptions could include a password or bearer
  link. Persist only application-owned payload/token/delivery/delivery-record phase
  codes; preserve leased retry, backoff and terminal dead-letter behavior.
- `web/public/assets/auth-recovery.js`, `platform-workspace.js`, `app.js` and
  `web/index.html`: add tenant recovery without introducing a Platform reset path.
  The token is read from a URL fragment, immediately removed with `replaceState`,
  and held only in memory. Handle fragment-only email navigation as well as a new
  document; clear password inputs after attempted confirmation. Bound fetches to
  15 seconds and show localized failures without displaying server/provider text.
- The five canonical locale files and generated English bootstrap provide the new
  labels. Shared auth layout and theme behavior are reused.

## Temporary credential envelope fail-closed boundary — 2026-09-11T13:20:31Z

### Expected result

Employee account creation and HR reset must accept only a valid server encrypted
credential envelope before writing. Active-secret reads and temporary-password
reveal must treat malformed or cryptographically tampered persisted values as
unavailable, with a bounded application response and no crypto/provider detail.

### Execution context

- Repository: ERP-System, root `main`, source baseline `a4b7982bcf10ac71d709740af80dc2e79991e1c5`.
- Worktree: existing unrelated changes were preserved; the root currently has 260
  dirty paths. The separate TASK-236 candidate worktree was not modified.
- Environment/actor: synthetic PGlite domain fixtures and a local authenticated API
  fixture, acted by Codex as the implementation/test actor.
- No SMTP, real provider, production PostgreSQL/RLS, deployment, push or secret was
  used. Demo/Codex OCR remains a separate synthetic, user-authorized capability
  check.

### Root cause and implementation

`createEmployeeAccount` and `resetEmployeeAccount` previously trusted the runtime
truthiness of a typed `credentialEnvelope`, while the active-secret path used the
same truthiness check and the reveal path passed persisted JSON directly to
`decryptToken`. TypeScript annotations do not validate persisted JSON, and a
cryptographically invalid envelope could therefore escape the bounded domain
error boundary.

The shared `isEncryptedToken` guard now runs before create/reset transactions and
when reading the active secret. `revealEmployeeTemporaryPassword` catches
cryptographic/authentication failures and maps them to
`temporary_credential_unavailable` (HTTP 404). Tenant scope, HR authorization,
transactional writes, session revocation and audit ownership are unchanged.

### Actual result

- Malformed create and reset inputs reject with `invalid_credential_envelope`
  (HTTP 400) before account or secret writes.
- A malformed persisted envelope makes active-secret and reveal operations fail with
  `temporary_credential_unavailable` (HTTP 404).
- A deterministic ciphertext tamper also fails with the same bounded 404.
- The API response contains neither the fixture value nor the underlying crypto
  error text.

### Verification

`npx vitest run src/modules/hr/employeeAccount.test.ts
src/api/employeeAccount.integration.test.ts --reporter=dot` passed **2 files /
16 tests** with exit code 0. The new tests cover malformed write inputs, malformed
persisted JSON, cryptographic tampering, bounded domain errors and sanitized API
responses.

### Acceptance boundary

This closes a local credential-custody hardening slice only. TASK-193 remains
**Blocked** because Platform Superadmin recovery, real SMTP/delivery and
production PostgreSQL/RLS recovery evidence still require the responsible identity,
mail and release owners. No task, GOAL criterion, checkpoint, status or count was
promoted by this source/test evidence.
