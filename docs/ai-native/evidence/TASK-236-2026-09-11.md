## State and failure transitions

The durable boundary is explicit in `src/modules/agent/durableWorkflow.ts` and the
`agent_workflow_run` / `agent_workflow_step` schema. The approval step is the only
place where a human decision is required; queueing never manufactures approval.

| Situation | Legal transition | Durable outcome after restart |
| --- | --- | --- |
| Prepared intent is queued | `queued → waiting_approval` | The approval step remains waiting; no Pack exists. |
| Approved intent is queued | `queued → queued` | The worker can claim the execute step. |
| Waiting intent is approved | `waiting_approval → queued` | The worker reloads the intent and current authority before the effect. |
| Waiting/paused intent is rejected, cancelled or expired | `waiting_approval/paused → cancelled/failed` | Terminal state is retained and cannot be resumed. |
| Queued work is paused | `queued → paused` | No effect is claimed until an explicit resume. |
| Paused prepared work resumes | `paused → waiting_approval` | A fresh approval is still required. |
| Paused approved work resumes | `paused → queued` | The worker rechecks module, grant, principal and exact intent. |
| Lease expires | `running → queued` on the next claim | The same run and effect key are recovered; attempt identity is retained. |
| Effect fails retryably | `running → queued` while attempts remain | Bounded attempts and `available_at` survive worker restart. |
| Effect fails terminally or attempts are exhausted | `running → failed` | Only a safe error code is retained; no false success is emitted. |
| Cancel before Pack commit | `queued/paused/running → cancelled` | No Pack is written for that run. |
| Cancel after Pack commit | `running → succeeded` | The committed Pack/PDF is reconciled and reported, never pretended to roll back. |
| Verified effect completes | `running → succeeded` | `resultRef` contains Pack ID, source hash, artifact hash and byte length. |
| Any terminal state is read | `succeeded/failed/cancelled → same state` | Terminal rows are immutable and replay is idempotent. |

Raw trigger keys and the separately supplied intent key are never copied into the
workflow row, outbox payload, audit detail or request identifier. Only SHA-256
trigger/effect references and the stored intent ID are retained.

## Recovery and compensation

The Pack write and workflow result reference share the governed tenant transaction.
If a future cross-system provider or renderer step fails after a Pack commit, the
worker must keep the same run/effect identity, inspect the persisted Pack and
`resultRef`, and reconcile the committed outcome. An operator may resume that same
run after repairing authority or the external dependency. The system must not replay
an uncertain effect with a new intent key or manufacture a second Pack. A terminal
failure remains terminal until an explicit, reviewed recovery action is added.
