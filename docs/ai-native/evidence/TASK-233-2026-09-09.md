## S2 — Exact intent persistence and expiry binding

S2 adds the Agent-owned `agent_execution_intent` aggregate in migration `0108`.
It is tenant-scoped by `master_fn` + `company_fn`, linked to the Agent principal
and accountable actor, and stores only a SHA-256 hash of the separately supplied
execution intent key. The raw key is not present in the row, reviewed facts or the
append-only audit payload; the module rejects a request identifier that contains it.

`prepareAgentExecutionIntentWithin` reuses the governed Pack selection query after
normalizing the Pack key, visibility, locale and inclusive date filters. The stored
reviewed facts include the complete normalized filters, actor/Company/action identity,
every selected receipt id/version, document id/version/hash, totals, counts, retention
deadline and the Pack selection digest. A canonical JSON digest binds those facts;
a second resource-version digest makes the receipt/document version boundary explicit.
The server assigns a 15-minute expiry and does not accept a client-selected expiry.
Same-key identical preparation replays the existing intent; changed reviewed facts
conflict.

Human confirmation is a separate command boundary. Approve, reject and cancel lock the
intent, require the expected version, require an active human member of the current
Company and require the current Receipt Pack read authority for the reviewed visibility.
The non-login Agent actor cannot decide the intent. Rejected and cancelled states are
terminal for execution; an approved intent may be cancelled before S3 execution.
The existing Agent `receipt_pack.create` dispatcher still returns 428 and no Pack row
is created; S3 owns the later atomic execution integration.

Expiry is enforced from the server-owned `expires_at` timestamp before approval or
verification. The rejecting transaction deliberately does not update the row to an
`expired` status before throwing: that update would roll back with the rejection and
would create misleading evidence. The persisted preparation remains auditable through
its expiry timestamp, while execution is fail-closed after the deadline. A future
committed maintenance transition may use the reserved `expired` status.

## S3 — Execute once with consistent facts

S3 connects the approved intent to the authenticated Agent `receipt_pack.create`
route. `dispatchAuthenticatedAgentAction` still resolves the issuer-derived
Company, active module, principal, accountable owner and current grant inside the
transaction; `executeAgentReceiptPackWithin` then locks the intent, rechecks the
identity-bound key, approval state and server expiry before touching the source
rows. The raw intent key is never written to the Pack or audit payload.

The Pack domain now has two explicit seams. `selectCompanyReceiptPackWithin`
accepts a `lockRows` option and uses `FOR UPDATE OF company_receipt` for
execution. `createCompanyReceiptPackFromSelectionWithin` inserts exactly the
already-reviewed selection and never performs an unconstrained second selection.
Agent Pack execution uses serializable tenant transaction isolation, source-row
locks and the existing Pack business-key unique/replay contract. A previously
committed Pack is checked before live-source revalidation, so a dropped response
can replay the immutable snapshot after a governed source correction; changed
payload reuse still conflicts.

The transport result is serialized as JSON after Agent field projection, so
date-time values in the domain projection satisfy the versioned output contract.
Pack creation and intent execution/replay append auditable events with Agent,
accountable-owner and intent/Pack digest attribution. The human
`POST /api/company-receipts/packs` path continues to call the original Pack
command and keeps its existing replay/conflict behavior.

## S4 — Handle replay and human corrections

S4 makes the committed-effect boundary explicit. The Agent dispatcher still
resolves the current principal, owner membership, grant window, scope and owner
permission before entering execution, so a replay cannot bypass a grant that has
expired or been revoked. Inside the execution command, supplied selection and
payload digests are checked before reading a replay. A Pack is replayable for a
cancelled intent only when the same intent already has an append-only
executed/replayed audit event; a Pack created by a human or another intent is
therefore a key conflict, not proof of Agent execution. An approved or cancelled
intent may discover its already committed immutable Pack without obtaining a new
approval; an uncommitted cancelled or rejected intent remains 428, and an
uncommitted expired intent remains 410.

Corrections use the existing optimistic-version updateCompanyReceiptWithin
command and the API's existing company_receipt update audit. No Pack row,
frozen receipt/document identity or original evidence is edited or deleted. The
corrected live receipt is version 2, while the committed/replayed Pack retains
the reviewed version-1 row facts.
